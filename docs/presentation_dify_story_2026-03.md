# 発表構成・台本

## タイトル案

- 非エンジニアの私が、AzureとOutSystemsを経てDifyにたどり着いた話

## 発表の芯

- 自分はエンジニアではない
- Azureでは何週間も試したが、重くて前進が遅かった
- OutSystemsも業務基盤としての意味は理解できたが、非エンジニアには重かった
- Difyにピボットしたことで、1週間で今の見積システムの形まで持っていけた
- しかも中身は単純なデモではなく、FP、部署別採算、人材レイヤー、他部署応援、営業利益率逆算まで含む実務寄りロジックになっている

## スライド構成

### 1. 自己紹介と問題意識

見出し:

- 非エンジニアの私が、AI見積システムを形にしようとした

載せるポイント:

- 自分はエンジニアではない
- それでも、AIを使って見積システムを業務に近い形で作りたかった
- 目指したのは、入力して結果が返るだけでなく、実務で意味のある見積ロジック

### 2. 最初にやったこと

見出し:

- まずAzureで試したが、重くて前に進まなかった

載せるポイント:

- AIエージェント接続やYAML設定を試した
- 何週間かけても、UIまで持っていけなかった
- 試作途中でも課金が発生した
- 「このままでは形になるまでが遠い」と感じた

### 3. OutSystemsでも試したこと

見出し:

- OutSystemsは理解できるが、自分には重かった

載せるポイント:

- NTT DATAでも採用されているローコード基盤として意味は理解できた
- 実際にDepartment dropdownを作り、部署で金額が変わるところまで確認できた
- ただし、型、データ、権限、公開、マスタ整備などの調整が多く、非エンジニアには荷が重かった

### 4. Difyにピボットして起きたこと

見出し:

- Difyに変えたことで、一気に前に進めた

載せるポイント:

- Vibe Coding的に試しながら進められた
- 1週間で、今の見積システムの形まで持っていけた
- 入力、計算、結果表示、レポート方向まで含めて短いサイクルで改善できた

### 5. Difyだから実現できたこと

見出し:

- ただ動くだけではなく、実務に近いロジックまで載せられた

載せるポイント:

- FPベースで規模を見る
- 部署ごとの間接費と販管費率を反映する
- Rank1〜Rank4の人材レイヤー構成で直接労務費を変える
- 他部署応援の配分も反映できる
- 目標営業利益率から逆算した推奨売価も出せる

### 6. 結論

見出し:

- 今回、自分にとって実現まで持っていけたのはDifyだった

載せるポイント:

- AzureやOutSystemsに意味がないとは思っていない
- ただ、今回の目的と自分の立場ではDifyが最も前に進めた
- Difyの価値は、非エンジニアでも試しながら実現まで持っていけることにある

## 台本

### 1. 自己紹介と問題意識

「今回の話で一番大きい前提は、私はエンジニアではないということです。それでも、AIを使った見積システムを業務に近い形で作りたいと思って動きました。単にAIっぽいデモを作りたかったわけではなく、実際の見積実務に近いロジックを持ったものを、触れる形にしたいと考えていました。」

### 2. 最初にやったこと

「最初はAzureで試しました。AIエージェント接続やYAMLの設定など、かなり本格的に触ってみました。ただ、何週間かけても前進が遅く、UIまで持っていくところまでたどり着けませんでした。しかも試作段階でも課金が発生していて、このやり方では形になるまでが遠いと感じました。」

### 3. OutSystemsでも試したこと

「次にOutSystemsも試しました。OutSystemsについては、NTT DATAでも採用されているローコード基盤として意味があることは理解していますし、業務システムに載せる文脈では有力だと思います。実際、Departmentのdropdownを作って、部署によって金額が変わるところまでは確認できました。ただ、型、データ、権限、公開、マスタ整備といった周辺調整の比重が大きく、非エンジニアが短期間で形にするにはかなり重いと感じました。」

### 4. Difyにピボットして起きたこと

「そこで途中からDifyにピボットしました。Difyを触りながら、いわゆるVibe Coding的に試していったところ、一気に前に進みました。結果として、1週間で今の見積システムの形まで持っていくことができました。入力を変えて計算結果を確認し、ロジックを直し、また試す、という改善サイクルを非常に短く回せたことが大きかったです。」

### 5. Difyだから実現できたこと

「ここで重要なのは、単に早く作れたということだけではありません。中身もできるだけ実務に近づけています。うちの会社では見積にFunction Pointが必須なので、画面数やテーブル数を簡易FPに換算して工数を出す形にしています。さらに、部署ごとの間接費や販管費率も入れています。」

「加えて、誰が関わるかによって人件費が変わるので、Rank1からRank4までの構成比を入力できるようにしています。つまり、部長級に近いレイヤーなのか、主任以下中心なのかで直接労務費が変わります。さらに、他部署が応援で入る場合の配分も反映できるようにしています。」

「そして最後に、原価や利益率を出すだけでなく、目標営業利益率から逆算した推奨売価まで出せるようにしています。ここまで入れることで、単なるAIデモではなく、実務に寄せた見積ロジックとして形にできたと思っています。」

### 6. 結論

「今回の経験を通じて、AzureやOutSystemsに意味がないと言いたいわけではありません。どちらも役割があります。ただ、今回のテーマと自分の立場では、実際に動くものまで持っていけたのはDifyでした。自分にとってDifyの価値は、単に簡単ということではなく、非エンジニアでも試しながら実現まで持っていけることにあったと感じています。」

## 発表で強調したい実務寄りポイント

- Function Pointベースで規模を見ている
- 部署別の間接費と販管費率を反映している
- Rank1〜Rank4の人材レイヤー構成を入力できる
- 他部署応援の配分を反映できる
- 目標営業利益率から逆算した推奨売価を出せる
