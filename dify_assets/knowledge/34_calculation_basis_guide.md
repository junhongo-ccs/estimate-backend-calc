# 見積算出ロジックの根拠と計算体系 (FY2026 BS事業部標準)

本ドキュメントは、Dify 上で動作する AI 見積システムの計算ロジックを、説明用ではなく**実装根拠**として整理したものである。  
狙いは、LLM が「なぜこの金額になったか」を説明する際に、案件固有の数値は `calc_json` を見つつ、背景ロジックは本ドキュメントを参照できる状態を作ることにある。

---

## 1. 本システムの役割分担

本システムは以下の 3 層で成立している。

1. **入力UI**
   - 画面数、テーブル数、部門、開発タイプ、追加機能などを受け付ける
2. **Python 計算エンジン**
   - 金額、工数、採算を deterministic に算出する
3. **LLM**
   - Python の計算結果を内部報告書の形に整形する

このため、案件固有の事実は Python 出力の `calc_json` を正とし、本ドキュメントは「背景説明」にのみ使う。

---

## 2. 積算の基本構造

本システムの見積は、以下の 2 系統を合算するハイブリッド方式である。

- **規模ベース積算**
  - 画面数とテーブル数から FP 相当規模を推計する
- **追加要素積算**
  - 高負荷機能
  - Phase 2 の設計・構案
  - Phase 3 の UI/デザイン系項目
  を別枠で加算する

したがって、基本式の考え方は次の通りである。

`総見積 = FPベース工数由来の原価 + 機能追加原価 + Phase2 原価 + Phase3 原価 + 部門別間接費 + 採算上の調整`

---

## 3. 規模推計のルール

### 3.1 基本重み

- 1画面 = **20**
- 1テーブル = **15**

Python 実装上は、以下のように扱う。

- `screen_fp = screen_count * 20`
- `table_fp = table_count * 15`
- `total_ufp = screen_fp + table_fp`

### 3.2 プロファイル別生産性

見積プロファイルごとに、人日/FP の係数を変える。

| プロファイル | キー | 生産性係数 |
| :--- | :--- | :--- |
| PoC/開発重視型 | `poc` | `0.075` |
| エンタープライズ型 | `enterprise` | `1.5` |
| 高信頼性型 | `mission_critical` | `2.0` |

規模ベース工数は次式で求める。

`FPベース工数 = total_ufp * productivity_factor`

## 7. 直接労務費

直接労務費は、総工数を人月換算したうえで、ランク別月額コストの加重平均を掛ける。

### 7.1 ランク別月額コスト

| ランク | 月額コスト |
| :--- | :--- |
| `Rank4` | 1,098,000 |
| `Rank3` | 944,000 |
| `Rank2` | 758,000 |
| `Rank1` | 541,000 |

### 7.2 標準チーム構成

指定がない場合は以下を使う。

- `Rank3`: 0.8
- `Rank2`: 0.2

### 7.3 算式

`人月 = 総工数(人日) / 20`

`直接労務費 = 人月 * ランク別月額コストの加重平均`

---

## 8. 間接費

間接費は、所属部門別の時間単価を総稼働時間に掛ける。

算式:

`間接費 = 総工数(人日) * 8時間 * 部門別間接費単金`

部門横断案件では `dept_allocation` に応じて加重平均する。

---

## 9. 販管費と採算評価

本システム実装では、販管費は**直接労務費に対する率**として扱う。

これは Dify 上の Python 実装と、内部報告書生成ロジックの整合を優先した現在の運用ルールである。

### 9.1 採算系の主要定義

- `sales` = 見積売価
- `cogs` = 売上原価
- `gross_profit` = `sales - cogs`
- `sga_cost` = `direct_labor_cost * sga_rate_on_labor`
- `operating_profit` = `sales - cogs - sga_cost`

### 9.2 目標利益率からの逆算売価

目標利益率 `target_margin` が与えられた場合、必要売価は次式で逆算する。

`suggested_price = (cogs + sga_cost) / (1 - target_margin)`

---

## 10. 最終売価の組み立て

Python 実装上の考え方は次の通りである。

1. 規模ベース工数を算出
2. 追加機能工数を加算
3. 直接労務費を算出
4. 間接費を算出
5. Phase 2 / Phase 3 の固定原価を加算
6. `cogs` を組み立てる
7. プラットフォーム倍率、期間倍率、共通バッファを掛けて最終売価を出す

最終見積額のイメージ:

`final_amount = cogs * platform_multiplier * duration_multiplier * buffer_multiplier`

---

## 11. RAG で拾ってほしいポイント

LLM が本ドキュメントから拾うべきポイントは次に限定する。

- 本システムは FP ベースと追加要素積み上げのハイブリッドである
- 画面数とテーブル数は固定重みで FP 相当に変換される
- 追加機能、Phase 2、Phase 3 は別枠加算である
- 部門別間接費とランクミックスが採算に効く
- 販管費は現在実装では直接労務費ベースで扱っている

逆に、案件固有の数値や項目名は必ず `calc_json` を優先し、本ドキュメントだけから推測してはならない。

---

## 12. 結論

本システムは、入力 UI の気軽さを保ちつつ、以下を同時に成立させる構造である。

- Python による deterministic な金額算出
- 部門差、ランク差、Phase 差の反映
- RAG による背景説明補強
- LLM による内部報告書整形

したがって、説明時には

- 事実 = `calc_json`
- 背景 = 本ドキュメント

の役割分担を守ることが重要である。
